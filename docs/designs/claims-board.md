## Problem Statement

v1 lets anyone turn a run into a claim (a public gist holding `claim.json`), and lets visitors reproduce or beat it
from the claim page. Reproductions are ` ```arena-repro ` blocks in the gist's comments. Two things are missing.

- **Nobody can find claims.** GitHub doesn't search gist contents, so a claim exists only for people who were handed
  the link. A developer choosing models for their agent still has no page that answers: *which setup leads on a task
  like mine, how sure is that, and which steps hold up?*
- **The author curates the evidence.** A gist owner can delete reproduction comments. v1 shows only tamper evidence
  (the `seen` ids) and says so on the page (v1 Open Question 1: "Decide before v2").

Goal: a public **claims board** that ranks claimed setups per scenario by performance, shows how sure each number is,
shows which steps worked, ranks models per role, and keeps reproductions it has recorded even if the author deletes
them. No server we run.

## What Makes This Cool

- **Performance first, honesty built in.** Reproduced claims rank by the low end of their pass-rate interval, so a claim
  that passed 11 of 11 tasks ([74–100]) sits below one that passed 95 of 100. As people reproduce a claim, its row moves
  toward the reproduced rate, up or down, so a cherry-picked best-of-N claim sinks. Unreproduced claims wait in their
  own list ("be the first to reproduce") unless the visitor merges them in.
- **You can see which steps worked.** Each row shows per-criterion pass rates (for `email_assistant`:
  `state_correct`, `no_collateral`, `answer_correct`).
- **A role ranking that is measured, not assumed.** Most per-role rankings reuse a model's general benchmark score.
  Here, a Beat-this run changes exactly one role and re-runs both setups on the same tasks, so its difference belongs to
  that role. "gpt-4.1 is +6 points as the tool-calling agent vs gpt-4.1-mini, measured by 4 swaps" is an experiment
  result. Where no swap exists yet, the board says "appears in N setups" in a visibly weaker style.
- **The board is a witness.** Once the board has recorded a valid reproduction, deleting the comment no longer removes
  it. The row says "1 reproduction removed by the author after the board recorded it (still counted)".
- **Every dot is a challenge.** Clicking a claim or "Beat this" opens the v1 claim page, where the visitor swaps one
  role and runs.

## Constraints

- **No server we run** (v1 premise 5). GitHub Actions, gists, issues and Pages only.
- **One engine, one rule set.** The Action validates with the same pure Python code the claim page runs in Pyodide:
  `check_claim`, `parse_repro`, `validate_repro`, `trust_stats`, `wilson` (`src/llm_arena/claims.py`). The board never
  reimplements a counting rule.
- **The engine stays pure.** Board aggregation (ranking, tiers, role effects) is a new pure module; all fetching sits
  in adapters (reuse `adapters/server/gists.py`: fixed API base, id checks, 2 MB cap, 10 s timeout).
- **Closed schemas.** Every new field is optional, closed and bounded, and exported to `contracts/`.
- **GitHub limits and auth.** The Actions `GITHUB_TOKEN` is a GitHub App installation token, and gist endpoints answer
  it with 403 (GitHub community discussion #126039); unauthenticated reads get 60 per hour per IP, shared on hosted
  runners. So the board reads gists with a repository secret `BOARD_READ_TOKEN`: a fine-grained personal access token
  with no permissions beyond public read, 5,000 requests per hour. Without the secret, the build refuses to run. Budget
  per claim and build: section 4.
- **Untrusted input everywhere.** Issue bodies, gist contents and comments are hostile until validated. Workflows never
  interpolate them into shell commands; they pass through files or environment variables.
- **Pages builds on push and manual dispatch today** (`.github/workflows/pages.yml`). The board adds a scheduled
  path that dispatches it.

## Premises

Agreed during the session (2026-10-11):

1. **No server.** An Action reads a registry, validates every claim and reproduction with the engine, and writes
   `board.json`. The existing SPA renders it at `#/board`. A schedule rebuilds it.
2. **Claims are submitted, not discovered.** "Submit to board" opens a prefilled issue. The Action validates the claim
   and rejects invalid ones with a reason.
3. **Rank by performance, sample-aware, among reproduced claims.** Sort by the low end of the pass-rate interval, then
   by step credit (the engine's partial credit). Cost is a column, never the sort key. Confidence is always visible: a
   tier (claimed, reproduced by 1–2, verified by 3+ people), the interval, and reproduced numbers replace claimed ones
   once reproductions count. *(The user rejected a blended score with cost; Codex challenged raw pass-rate ranking,
   which led to the sample-aware sort.)*
   *(Amended after spec review R1-9, user decision D3.)* Claim numbers are author-written, so only claims with at least
   one counted reproduction by someone else enter the ranking. Unreproduced claims form a second list below, sorted
   the same way, inviting reproduction. A two-state switch ("Reproduced only" / "Include unreproduced") merges both
   into one ranking with claimed rows marked. It defaults to merged while a scenario has no reproduced claim (the
   launch state) and to "Reproduced only" otherwise; the viewer's choice is remembered per browser.
4. **"Which steps worked" = per-criterion pass rates**, added as an optional field to new claims and reproductions.
   v1 claims show without it.
5. **Role ranking, tiered by confidence.** Paired one-role swaps are the high-confidence tier ("measured by N swaps").
   Appearance-based numbers (how setups that use a model in that role perform) are the low-confidence tier ("appears in
   N setups"). A measured entry replaces the appearance-based one for the same model and role group.
6. **Hand-seeded.** The user publishes 6–10 claims across the claimable scenarios before announcing the board, at least
   two per seeded scenario so rows compete.

## Cross-Model Perspective

Codex (gpt-5.5), cold read of the session summary:

- **Coolest version:** a "scenario recipe atlas": winning setups drawn as pipelines (`agent → critic → writer →
  decider`), each role colored by model and annotated with criterion pass rates; click a role to see what swapping it
  did to each criterion. Killer query: "the cheapest setup above 80% pass rate where the critic is strong and the
  tool-calling agent is replaceable."
- **Revealing quote:** "It should be clear which steps worked well." The excitement is attribution, not trophies.
- **Halfway there:** SWE-bench-style static leaderboard infrastructure (validated submissions, static site). The other
  half is llm_arena-specific: claim and repro validation, paired swaps, criterion aggregation, role rankings,
  confidence tiers, tamper evidence.
- **Weekend build:** registry + Action emitting `board.json` + `#/board` (scenario selector, table, confidence filter,
  scatter) + claim detail + issue template + seed at least two claims per scenario. Role rankings second.
- **Challenged premise:** ranking by raw pass rate lets expensive frontier stacks and low-N claims lead. Resolved by the
  sample-aware sort (premise 3), without bringing cost into the ranking.
- **Author curation:** recommends independent `arena-repro` gists as first-class indexed evidence. This design takes the
  cheaper witness ledger first and keeps repro gists as a follow-up (Open Questions).

Design voices on the wireframe:

- **Codex: "evidence poster".** Chart as an unframed visual anchor; dense ranked table with role chips colored by the
  existing `--kind-*` tokens; `--accent` only for the selected claim. Interactions: *Frontier scrub* (focus a dot →

## Approaches Considered

- **A: Registry file + scheduled build.** Minimal; the maintainer adds claims by PR; a deleted reproduction disappears
  on the next build. Not chosen: author curation would quietly reshape the board.
- **B: A + witness ledger + self-serve submissions.** **Chosen.**
- **C: The board's own issue threads.** Reproductions move to one repo issue per claim, moderated by the maintainer.
  Not chosen: reworks v1's posting path, needs a broader `public_repo` token and makes the maintainer everyone's
  moderator.

## Recommended Approach: B, witness ledger and self-serve submissions

### 1. Schema additions (optional, closed, bounded)

- `ClaimResult.criteria: dict[str, CriterionResult] | None` with `CriterionResult {passed: int ≥ 0, graded: int ≥ 1}`;
  at most 16 entries; names must be the scenario's pass criteria; `passed ≤ graded ≤ trials`. `graded` counts the
  trials in which that criterion produced a verdict (a trial that errored before reaching it doesn't count). Computed
  in `claim_from_run` from the per-trial scores in `RunData` (the eng review names the exact field; today
  `claim_from_run` reads only `passed`, `credit` and `cost_usd`).
- `ReproSide.criteria` (same shape) and `ReproSide.partial: float | None` (0–1), filled by `repro_from_run`, so
  reproduced numbers can replace claimed step numbers.
- **Validation (R1-15):** `check_claim` and `validate_repro` apply the same rules to the new fields: known criterion
  names only, at most 16, `passed ≤ graded ≤` that side's trials, `partial` in [0, 1]. New conformance vectors cover a
  valid and an invalid case of each, replayed by the Pages selftest.
- **Hash stability (R1-1):** `claim_hash` must not change for existing claims. Fields added after v1 are dumped into
  the hash input only when set (`exclude_none` scoped to those fields), so a stored v1 claim hashes exactly as before
  and its reproductions and `parent_claim_hash` links stay valid. A conformance vector pins the hash of a stored v1
  claim under the new engine, in Python and in Pyodide.
- **Compatibility risk:** v1 engines reject unknown fields (`extra="forbid"`), so a local app on the v1 release would
  refuse a claim that sets `criteria` (Open Question 1).

### 2. Data branch `board-data`: registry, claim cache, ledger

- `board/registry.json`: `[{gist_id, revision, claim_hash, owner_login, owner_id, submitted_by_id, issue, added_at}]`,
  capped at 200 entries. A `removed` list (append-only) lets the maintainer delist a claim with a reason, shown on the
  board as "delisted: <reason>" for 30 days.
- `board/claims/<claim_hash>.json` (eng re-review D9): the pinned `claim.json` content, cached at submission and
  verified against its `claim_hash` on every build. The revision is pinned, so the
  content can't change; builds never refetch it, and a row survives if the author deletes the whole gist.
- `board/ledger.jsonl`: append-only, one line per recorded reproduction: `{gist_id, comment_id, user_login, user_id,
  created_at, recorded_at, block_sha256, repro, prev_sha256}`, where `repro` is the validated block (its numbers
  survive deletion) and `prev_sha256` chains each line to the previous one.
- `board/board.json`: the built output (sections 4–6), committed so history is diffable.
- **Append-only, enforced (R1-8):**
  - A repository ruleset on `board-data` blocks force pushes and branch deletion with no bypass actors. Ordinary
    fast-forward pushes from the board workflows still work; this is verified in a test run before launch.
  - Every build checks that the previous `ledger.jsonl`, `registry.json` entries and `removed` list are exact prefixes
    of the new ones, that the ledger's hash chain verifies, and that every cached claim matches its `claim_hash`
    (eng re-review D10); otherwise it fails and writes nothing. Registry entries are never edited: a wrong entry is
    delisted through `removed` and resubmitted.
  - A CI check (`actionlint` plus a grep rule) fails if any workflow other than `board-submit.yml` and `board.yml`
    pushes to `board-data`.
  - Identity uses numeric GitHub user ids where the API gives them, so renamed accounts stay one person.

### 3. Submission (`.github/ISSUE_TEMPLATE/claim.yml` + `.github/workflows/board-submit.yml`)

- After publishing, the claim page shows **Submit to board**, linking to
  `github.com/tilt/llm_arena/issues/new?template=claim.yml&gist=<id>&revision=<sha>`. The template adds the
  `claim-submission` label; the visitor is signed in to GitHub, so the issue author is the submitter.
- `board-submit.yml` (on `issues: opened`, label `claim-submission`) runs `arena board submit --issue <number>`:
  1. Read the issue body from the event payload file, never through `${{ }}` in `run:`; extract the gist id and
     revision with the v1 patterns.
  2. Before any gist request: reject if the submitter already has 5 submissions (accepted or rejected, counted from the
     issue list by label and author) in the last 24 h, or if the registry is full.
  3. Fetch the pinned claim (1–2 requests), `check_claim`, require state `ok` (not drifted), require that the issue
     author's id equals the gist owner's id, and dedupe by `claim_hash`.
  4. Accept: append to `registry.json`, write `claims/<gist_id>.json`, push fast-forward only, comment "added", close,
     and dispatch `board.yml`.
- **Outcomes (R2-2).** *Rejections* are the claim's fault (invalid, drifted, foreign owner, duplicate, over the
  limit): comment the reason, close as "not planned"; they count toward the 5-per-24 h limit. *Infrastructure failures*
  (gist timeout or 5xx, 401/403 from `BOARD_READ_TOKEN`, rate limit, push failure) leave the issue open with the label
  `board-retry` and a "will retry" comment, and don't count toward the limit. Only per-issue failures count as attempts (a timeout or 5xx on that gist, a crash
  while processing that body, a push rejected for that run); the counter is the number of the bot's "will retry"
  comments on the issue. After 3 such attempts the issue closes with the label `board-internal-error` and the comment
  "resubmit; this does not count toward your limit", and the workflow fails so the maintainer is notified. Global
  failures (`BOARD_READ_TOKEN` 401/403, rate limit) abort the whole run without using any issue's attempts, keep every
  issue open with `board-retry`, and fail the workflow with a message naming the cause. The 24 h limit counts only
  accepted issues and rejections without `board-internal-error`. Tests: a 5xx, a 401, a push failure, and a dead token
  across more than 3 sweeps (submissions stay open and are accepted once the token works).
- **One write protocol (R2-1).** `board-submit.yml` and `board.yml` share one concurrency group, `board-data`, with
  `cancel-in-progress: false`, so only one of them writes the branch at a time. Each run reads `board-data` fresh at
  its start, does all checks (dedupe, cap, limits, ledger prefix and chain) on that state and pushes fast-forward only.
  If a push is still rejected (a human push), the run fails without retrying a stale merge: a submission stays open for
  the sweep; a build keeps the previous `board.json`. A pending run dropped by the concurrency group is recovered by
  the sweep. Test: a submission arriving during a build is processed by the next run or the sweep, never lost.
- **Missed runs are recovered (R1-6).** `board.yml` first sweeps every open `claim-submission` issue through the same
  command, reading each issue's current body through the API and skipping the `board.yml` dispatch. Processing is
  idempotent (keyed by issue number and `claim_hash`).
- **Tokens (R2-3).** `BOARD_READ_TOKEN` is used only for gist reads (head, pinned revision, comments); the adapter
  takes it from that named environment variable and refuses to start without it. The check applies only to the real
  HTTP transport; fixture and injected-transport builds (tests, CI dry run, local runs) need no secret. `GITHUB_TOKEN` does everything else:
  reading and commenting on issues, closing them, `gh workflow run`, and git pushes.
- **Permissions (R1-7):** `issues: write`, `contents: write`, `actions: write` (for the dispatch).

### 4. Build (`.github/workflows/board.yml`)

- **Triggers:** schedule every 6 hours, `workflow_dispatch` (from `board-submit.yml` and manual). **Permissions:**
  `contents: write`, `issues: write` (sweep), `actions: write` (dispatching `pages.yml`). Concurrency group
  `board-data`, shared with `board-submit.yml`, not cancelled in progress (section 3).
- `arena board build` (fetching in an adapter on top of `adapters/server/gists.py`; everything else in the pure
  `llm_arena/board.py`):
  1. Sweep open submissions (section 3).
  2. For each registry entry: one head request (`GET /gists/{id}`: comment count, existence), then only the comment
     pages that count needs, at most 3 (the v1 cap of 300 comments). The claim comes from the cache.
  3. Merge with the ledger: each valid reproduction not yet recorded is appended. A recorded reproduction whose comment
     is gone counts from its ledger copy, flagged `removed_after_recorded`. A recorded comment edited later keeps the
     recorded version, flagged `edited_after_recorded`.
  4. Run `trust_stats` over the merged thread (ledger copies stand in for deleted comments), so counting stays the v1
     rule: latest per user, author excluded, same judge, same task set, both engines pooled (the claim page default).
     v1's own `removed` count (comments referenced by `seen` that the board never recorded) is shown as on the claim
     page.
  5. Rank (section 5), build role effects (section 6), write `board.json` (closed schema in `contracts/`, at most
     2 MB).
- **Budget (R1-2):** at most 4 requests per claim per build (head + up to 3 pages); 200 claims cost at most 800 of the
  token's 5,000 per hour. Submissions cost 1–2 each. Before each claim the build reads `X-RateLimit-Remaining`; below
  what the rest of the registry needs plus 100, it stops and keeps the previous `board.json`.
- **Per-entry outcomes (R1-4), each with a test:**
  - Gist deleted or 404: the row stays and keeps its rank, built from the cache and the ledger, flagged "gist deleted
    by its author". Its claim link and Beat this are disabled (the claim page needs the gist).
  - Timeout or 5xx: one retry, then the last good row stays, flagged "not refreshed since <date>".
  - `check_claim` newly fails: scenario drift moves the row to "older versions"; any other failure (for example a
    model dropped from the price table) keeps the row in place and in rank with "no longer runnable: <reason>" and
    Beat this disabled.
  - Global failure (rate limit, more than 20% of entries failing, output over 2 MB, ledger prefix check failing): the
    build fails and the previous `board.json` stays published.
- **Chaining (R1-7):** after committing `board/` to `board-data`, `board.yml` runs `gh workflow run pages.yml`
  (`workflow_dispatch`, allowed for `GITHUB_TOKEN`). `pages.yml` (its deploy job `needs: board`, so the commit lands first) runs `git fetch origin board-data` and
  `git show origin/board-data:board/board.json > web/dist/board.json`, skipping the copy when the branch or file
  doesn't exist yet (before launch), before upload, so the board loads same-origin. `actionlint` runs on all workflows
  in CI, and a dry-run job builds `board.json` from a fixture registry with mocked GitHub.
- The local app serves the board through a small `/api/board` proxy or links to Pages (CSP `connect-src 'self'`
  stays); Open Question 4.
- **What the witness can't catch**, stated on the board: a reproduction deleted before the first build that saw it (up
  to 6 hours), comments beyond the first 300, and a ruleset change by the repository owner.
- **Threat model for reproductions (R2-4).** Like v1's claim page, the board treats a reproduction as self-reported:
  `validate_repro` checks consistency, not that a run happened, and "someone else" means another GitHub account. One
  person with several accounts can move a claim into the ranking, reach "verified", or create measured role entries.
  The board accepts this, as v1 does, and makes it visible: every ranked row and every measured role entry lists the
  reproducers' logins (expandable), and the board's "what this can't catch" note says "reproductions are self-reported;
  a person controlling several accounts can inflate a claim". A stricter filter is Open Question 7. Test: every ranked
  row and measured entry exposes its reproducer ids.

### 5. Ranking (pure, in `board.py`)

- **Performance number:** with counted reproductions, the pooled reproduced rate; otherwise the claimed rate. Step
  credit and per-criterion rates are pooled the same way, weighted by trials. **Cost** shows the claimed cost for
  claimed rows and the trial-weighted reproduced cost once reproductions count (labeled).
- **Interval (R1-10):** the ranking interval is task-level. Each task's pass share (over repeats and reproducers)
  counts once, so the effective sample size is the number of tasks, not tasks × repeats. Raising repeats doesn't
  inflate rank, and more reproducers move the number rather than shrink the interval below what the task count
  supports. The task count shows next to the interval. The v1 claim page keeps its trial-level interval for now;
  aligning it is a follow-up.
- **Claimed rows (factual correction, eng re-review):** a claim carries no per-task counts, so its task-level
  interval uses rate = passed / trials with n = number of tasks; reproduced rows use the per-task shares from the
  stored `Repro.per_task`. Both live in `claims.py` next to `wilson`.
- **Sort:** among reproduced claims (premise 3, D3): task-level Wilson low end, descending; then step credit; then
  more people; then claim date. Unreproduced claims are sorted the same way in their own list, or merged with a
  "claimed" mark when the switch says so.
- **Tiers:** claimed (0 people), reproduced (1–2), verified (3+), matching v1's threshold for the "above interval" note.
  "People" means distinct GitHub accounts (see the threat model in section 4); the board's "what this can't catch"
  note says so next to the tiers.
- **Within a scenario version and task set only.** Different scenario versions or task sets never share a table.

### 6. Role ranking (pure, in `board.py`)

- **Role groups:** from `RoleRequirement.kind` (`agent` → Tool calling, `code` → Code, `vision` → Vision, `decision` →
  Decision) plus one new optional `RoleRequirement.skill` that splits `text` roles into Writing (`writer`,
  `copywriter`) and Critique (`critic`, `reviewer`). Decision-service swaps (repro variant shape (b), which changes
  `decisions` rather than a role, R1-11) belong to Decision, with the service policy as the entry (for example
  "policy: jev"). Tested.
- **Entry identity (R1-14):** provider + model + `reasoning_effort` + `tool_mode`, since those change behavior.
  Temperature and `max_tokens` are pooled and shown when they differ. Self-hosted entries appear under their
  declared name with v1's "self-declared" caption.
- **Measured tier, and its inputs (R1-12):** every valid reproduction with a variant is a one-role swap, whether
  counted, superseded or the author's own. Per (user, claim, role, entry), the latest swap is used. The aggregation
  re-parses the stored `Repro` objects (ledger copies) for their `per_task` pairs, since `trust_stats` rows don't carry
  them. Within a role group, entries connected by swaps go on one scale relative to a reference entry with an
  interval: "+6 pts vs gpt-4.1-mini · measured by 4 swaps · [+2, +10]".
- **Author swaps (R1-13, decided):** they count, which seeding needs, and they're labeled. An entry backed only by
  claim authors' swaps shows "measured by N swaps, all by claim authors" in the measured style with a lighter fill.
  They count toward the 2-swap minimum.
- **Appearance tier:** for entries with no swap in that group: the mean performance of claims that use the entry in a
  role of that group, labeled "appears in N setups", in the muted style, never on the measured scale.
- **Minimums:** a measured entry needs at least 2 swaps; an appearance entry at least 1 claim.
- The estimator (pooled paired deltas per pair vs one fitted scale per group), the reference choice and pooling across
  scenarios are eng-review decisions (Open Question 2). The labels and tiers above are fixed.

### 7. Board UI (`#/board` in the existing SPA)

- Layout as in the wireframe: scenario tabs; pass-rate-vs-cost chart (dot = claim, size = people, fill = tier, interval
  bar); ranked table (setup chips, performance with interval and task count, steps that worked, tier, cost/task, Beat
  this); the unreproduced list below it with "Be the first to reproduce (about $X)"; the "Reproduced only / Include
  unreproduced" switch; "Best models by role" with role-group tabs; build time and counts in the footer; "older
  versions" collapsed.
- Rows flagged by the witness show their note under the row ("1 reproduction removed by the author after the board
  recorded it (still counted)", "gist deleted by its author", "not refreshed since …").
- Self-hosted roles keep v1's "self-declared" caption. Claims needing the local app show v1's "reproduce in the local
  app" hint.
- Visual decisions (interval strips, linked hover, unframed chart) go to /plan-design-review with the two design voices
  above as input.
- **Empty and partial states:** no claims for a scenario (tab hidden), no reproduced claims yet (merged view by
  default), no role evidence ("No swaps measured yet — Beat a claim to add one"), build older than 24 h (stale note),
  `board.json` missing (the claim routes still work).

### 8. Seeding (the user, before announcing)

6–10 claims across the claimable cloud scenarios (for example `email_assistant`, `support_desk`, `shop_codeact`,
`reflection_writing`), at least two per scenario, submitted through the real issue flow, plus a few Beat-this swaps of
the user's own claims. Those swaps fill the role ranking as "all by claim authors" (section 6) until others add
theirs. At launch every claim is unreproduced, so the board opens in the merged view.


### 9. Board design (plan-design-review, 2026-10-11)

Decisions from the design review. They refine section 7 and override the wireframe where the two differ. The
`#/board` route renders outside the engine gate (eng review D2).

- **Order (design 1A):** table first, chart second. The page reads top to bottom:

  ```
  ┌───────────────────────────────────────────────────────────────┐
  │ h1  Claims board                              [Submit a claim] │
  │ p.lead  answer line (2A)                                       │
  │ scenario tabs (3A): email_assistant v2 · support_desk v1 · …   │
  ├───────────────────────────────────────────────────────────────┤
  │ h2  Ranked setups            [Reproduced only | Include unrep.]│
  │ ranked table (reproduced claims, sample-aware sort)            │
  ├───────────────────────────────────────────────────────────────┤
  │ h2  Waiting for a first reproduction (N)                       │
  │ unreproduced list (hidden when merged)                         │
  ├───────────────────────────────────────────────────────────────┤

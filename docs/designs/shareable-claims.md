## Problem Statement

Developers choosing models for their own agent pick from generic leaderboards and vibes. None of those answer the
question they actually have: *which per-step model combination is the cheapest one that still passes an agentic task
like mine?* llm_arena already measures exactly that (a model per role, code-graded scenarios, per-task cost, paired
replacement studies), but every result stays on the machine that produced it. On GitHub Pages, results live only in
the visitor's IndexedDB (`web/src/lib/worker-backend.ts`, `leaderboard()` pools `listBundles()` of this browser).

Goal: let one person turn a run into a **shareable claim** that anyone can open, check, and try to beat, with the
reproductions accumulating where everyone can see them.

## What Makes This Cool

- **A claim, not a ranking.** The link says "setup S passes `email_assistant` v2 at 91% for $0.004 per task", with
  traces, and invites the visitor to *beat it*: swap one role, run, get a paired result on the same tasks. For the target
  dev this is a procurement argument: "what can I safely downgrade?"
- **Visitors are the verifiers.** A "Beat this" run re-runs the sender's baseline alongside the variant. Every visit is
  therefore also a reproduction of the original claim. The claim page shows "claimed 91% · reproduced by 5 people at
  86% [79–91]", and a cherry-picked best-of-N claim gives itself away as reproductions settle below it. No central
  authority decides whom to trust.
- **No server to run.** GitHub Gists are the store, the identity and the moderation.

(Numbers in examples are illustrative. `email_assistant` is currently version 2 with 11 tasks.)

## Constraints

- **Claimable scenarios:** the arena's own pattern scenarios only (`email_assistant`, `chart_codegen`, `launch_brief`,
  `react_multihop`, `reflection_*`, …). **Benchmarks (`gsm8k`, `mmlu_pro`, `humaneval`, `mbpp`, `ifeval`,
  `function_calling`) are not claimable in v1**, because a published bundle would redistribute dataset content that
  AGENTS.md says is downloaded at runtime and never vendored. No bring-your-own tasks. The scenario version plus the
  task fingerprints pin comparability.
- **The engine stays pure.** Claim/repro models, conversion and validation are engine code (pure, Pyodide-safe). All
  GitHub I/O lives behind the existing `Backend` interface (`web/src/lib/backend.ts`). The worker backend fetches
  GitHub directly on Pages, and the local app proxies through a server adapter (see "Gist I/O").
- **Pages runs remote models only.** `src/llm_arena/adapters/browser/arena.py:206` rejects local models, and
  `worker-backend.ts:91` hides presets that need Ollama, LM Studio or Ollaya/Jev. Local models and decision services
  exist only in the local app (`make ui`).
- **The visitor pays.** Runs use the visitor's own keys and run under `budget_mode: strict` with a cap shown before Run
  (see "Cost").
- **The security posture holds.** The local app keeps `connect-src 'self'` (`src/llm_arena/server/app.py:197`).
  Claims are untrusted input: closed schemas, allow-listed fields, text-only rendering. GitHub tokens follow the
  `credential-storage.ts` rules (memory by default) and are never written into a claim, repro or bundle.
- **Claims carry setups and results.** A claim never contains prompts, tools or task content; those come from the
  scenario at that version. *(Eng review D13: no `bundle.json` in v1; claims carry setup and results only. See TODOS.md.)*

## Premises (agreed)

1. The unit of value is a **claim** ("setup S passes scenario X vN at p% for $c/task", with traces), not a ranking.
   Audience: devs choosing models for their agent.
2. Curated scenarios only. Scenario version plus task fingerprints pin comparability.
3. *(Corrected during the session.)* On Pages, the claim page runs OpenAI/Anthropic models only, with the visitor's keys.
   The **local app serves the same claim route** and adds discovered local models (Ollama, LM Studio) and decision
   services (Ollaya/Jev). A claim whose baseline needs either shows "reproduce in the local app" on Pages. The cost cap
   always comes before Run.
4. Trust comes from replication, not authority. "Beat this" re-runs the baseline alongside the variant, and a number
   reads "claimed" until it is reproduced.
5. *(Amended after the second opinion.)* No server we run in v1. v1 **must** define a return path, so reproductions
   reach the claim (gist comments) and the claim page tallies them. A pooled public board is v2.
6. Distribution is the link itself, on the existing Pages deploy and in the local app. No new package.

## Cross-Model Perspective (Codex, gpt-5.5, cold read)

- **Coolest version:** a "claim duel". A locked challenge card (scenario, version, task fingerprints, baseline setup
  hash, claimed rate and cost). The visitor replaces one role, sees the cost, and gets a paired result such as
  "-3% pass, -61% cost, p=0.04". "A tiny reproducible buying argument, not a leaderboard row."
- **The tell:** "cheapest setup that passes my kind of task". The excitement is "turning model selection from vibes
  into a practical procurement move: what can I safely downgrade?"
- **Closest tool:** LLM Comparator (a single HTML page, sessions published as GitHub Gists, calls go browser to
  provider with the visitor's keys). It covers the distribution mechanic. The other 50% (code-graded scenarios,
  fingerprints, replacement studies) is what llm_arena already has. "Copy its distribution mechanic, not its product."
- **Challenged premise #5:** "Replication is only exciting if reproductions accumulate visibly. If every visitor's
  result dies in their own IndexedDB, the claim never becomes more trusted." This led to the amended premise 5.
- **Weekend build it proposed:** a hash-link "Beat This Setup" first, storage later. The user chose to include the
  public thread from v1 (see below).

## Approaches Considered

- **A: "Beat This" hash link.** The claim lives in the URL hash, and reply links carry reproductions. Not chosen: the
  tally lives in one browser, so "reproduced by N" never becomes public. *Kept as the no-GitHub fallback inside B.*
- **B: Gist-backed claims with a public reproduction thread.** **Chosen.**
- **C: "Downgrade ladder".** One click walks each role down a price-sorted ladder of cheaper models. Not chosen for v1

## Recommended Approach: B, gist-backed claims

### 1. Claim format (`claim.json`, closed schema exported to `contracts/`)

```jsonc
{
  "arena_claim": 1,
  "scenario": "email_assistant",
  "scenario_version": "2",
  "tasks": [{"id": "archive_newsletters", "fp": "3f0c9a1e"}, …],  // claim order; fp = task_fingerprint(task)
  "task_fps_hash": "…",          // _digest([[id, fp], …] in claim order), the canonical JSON of runner/fingerprint.py
  "seed": 0, "repeats": 1,
  "setup": {"roles": {…}, "params": {…}, "decisions": {…} | null},   // exactly fingerprint.setup_of() output
  "setup_fp": "a71e…",           // fingerprint(setup); recomputed on load, mismatch → rejected claim
  "result": {"passed": 10, "trials": 11, "pass_rate": 0.909, "partial": 0.95, "cost_usd_per_task": 0.0041,
             "engine": "pages" | "local"},
  "made_at": "…", "arena_version": "…"
}
```

- **Schemas are closed** (pydantic `extra="forbid"`, JSON Schema `additionalProperties: false`) for the claim, the
  repro and every nested object.
- **`setup.roles[*]` holds only `SPEC_FIELDS`** (`provider, model, backend, tool_mode, temperature, reasoning_effort,
  max_tokens`). Endpoint, key, `base_url`, `api_key_env` and `extra_body` fields cannot appear, because the closed
  schema rejects them.
- **Allow-lists:**
  - Providers: `openai`, `anthropic` and `openai_compatible` (named endpoints, portable role without endpoint
    fields; re-review R15) everywhere, plus `ollama` and `lmstudio` in the local app only.
  - `params`: every key must be a key of the scenario's `default_params` (`scenarios/base.py`). Its value must equal
    the default, or be one of `param_choices[key]`. A param without declared choices must equal its default. Scenarios
    declare no numeric bounds, so this is the whole rule.
  - `decisions`: only policy kinds `DecisionConfig` defines; Ollaya/Jev services in the local app only.
  - The card shows all params and the control policy above the Run button.
- **Metrics, defined to match the leaderboard:**
  - `pass_rate` = mean over tasks of the per-task pass share. With uniform repeats this equals `passed / trials`,
    which a valid claim requires.
  - `partial` = mean over tasks of the per-task partial credit (as in `report/leaderboard.py`).
  - `cost_usd_per_task` = total run cost / number of tasks.
- **Portability (setup → runnable config, lossless):**
  - Each role converts to a model ref with settings after `#` (the `_SETTINGS` of `llm/registry.py`).
  - **New ref setting `max_tokens`** (Next Step 1): `_SETTINGS` gains `"max_tokens": "max_tokens"` (an int), so
    `openai:gpt-4.1-mini#reasoning=none,max_tokens=4096` is a complete, portable role. `max_tokens` is already in
    `SPEC_FIELDS`, so it is part of `setup_fp`.
  - **Every priced role in a claim must have a finite `max_tokens`.** Strict budgets need it:
    `BudgetGuard.validate_spec` (`runner/budget.py:102`) rejects a priced model with `max_tokens=None`, and
    `ModelSpec.max_tokens` defaults to `None`. A claim without a finite `max_tokens` could never run under the visitor's
    strict cap.
  - A setup is **claimable only if every role is expressible that way**: an allowed provider, the default `backend`,
    and a finite `max_tokens` on every priced role. Otherwise Share as claim is disabled with the reason. For a run
    without `max_tokens`, the reason is "set max_tokens on agent (e.g. `#max_tokens=4096`) and re-run to make this
    claimable". The setup page's model picker offers the setting next to thinking.
  - **Every role must have a known price after portable resolution**: `explicit_or_known_price(resolved spec)` is not
    `None`. Explicit YAML prices aren't in `SPEC_FIELDS` and don't travel. Otherwise Share as claim is disabled ("critic
    has no known price; strict budgets can't run it").
  - Test: a portable cloud claim's resolved specs pass `BudgetGuard.validate_spec` in strict mode.
  - **Before Run**, the page resolves the baseline's specs on this machine and compares `fingerprint(setup_of(…))` with
    `setup_fp`. On a mismatch, Run is disabled with the differing fields, so nobody pays for an unpostable run.
    **After the run**, the engine recomputes the executed baseline's fingerprint as a guard. If it differs, the result
    is shown but cannot be posted.

### 2. Making a claim ("Share as claim")

- Offered on a **single finished run** (run report and run view), not on a leaderboard entry. A leaderboard entry links
  to its source runs instead.
- The run must have one config, uniform repeats, a single seed, and every task of its task list finished.
- **One exception: "Share my variant as a new claim"** after a Beat this run (two configs: `claim-baseline` and
  `swap-…`).
  - The new claim is built from the **swap config's trials only**, with the parent claim's tasks, seed and repeats.
  - The variant setup must pass the same claimability and portability checks; otherwise the button is disabled with
    the reason.
  - Its `result` is computed from the swap trials with the same definitions as section 1.
  - The swap trials must meet the same completeness and zero-error rules as any claim. Errors in the
    `claim-baseline` config do not block sharing the variant, because the variant claim makes no statement about the
    baseline.
  - The new claim records `"parent_claim_hash"` (an optional field in the closed schema). It is **verified on load**:
    the parent must resolve to a claim with the same scenario, version, `task_fps_hash`, seed and repeats, and the two
    setups must differ by an allowed rule-8 shape. Otherwise the link is not shown.
  - **Wording is neutral:** "variant of <parent>", plus the paired deltas from the sharer's run, labeled
    "self-reported". The page never prints "beats"; the trust strip of each claim speaks for itself. Test: a worse
    variant renders "variant of", and an unverifiable parent hash renders no link.
- Error, timeout and budget-stopped trials make the run unclaimable.
- *(Eng review D13: no `bundle.json` in v1. The redacted evidence format is a v1.1 TODO.)*
- The gist is **public** (claims are meant to be found; secret gists are only obscure, not private), with the
  description `llm_arena claim · <scenario> v<version>`.

### 3. Claim identity and edits

- A link pins the gist revision: `#/claim/gist/<id>@<revision-sha>`, plus `claim_hash` = full-length **SHA-256** of the canonical claim JSON (a separate helper, not the 12-character
  `_digest`, so an author can't grind a free field into a collision).
- The page loads the pinned revision (`GET /gists/{id}/{sha}`). If the gist's head revision differs, it shows
  "edited since this link was shared", with a toggle to view the head.
- A reproduction names the `claim_hash` it reproduced and counts **only toward that hash**. Editing the claimed number
  therefore starts a new, unreproduced claim.
- **Edited comments** (`updated_at > created_at`) are shown with "edited" and not counted.
- **The fallback without GitHub:** `#/claim/<base64url(claim)>`. It runs the same loop, with no thread or tally, and
  shows "Copy comment" for whoever does have the gist.

### 4. Reproduction comment (gist comment, one fenced block)

````
```arena-repro
{"arena_repro": 1, "claim_hash": "…", "scenario_version": "2", "task_fps_hash": "…",
 "baseline": {"setup_fp": "a71e…", "passed": 9, "trials": 11, "errors": 0, "timeouts": 0, "budget_stopped": 0,
              "cost_usd_per_task": 0.0043},
 "variant": {"setup": {…}, "setup_fp": "…", "passed": 9, "trials": 11, "errors": 0, "timeouts": 0,
             "budget_stopped": 0, "cost_usd_per_task": 0.0024} | null,
 "per_task": [{"b": 1, "v": 1}, {"b": 0, "v": 1}, …],
 "engine": "pages" | "local", "arena_version": "…"}
```
````

**`per_task`**: one entry per claim task, in claim order. `b` and `v` are pass counts out of `repeats`. When `variant`
is null, every `v` is null.

**A reproduction counts only if all of these hold:**
1. It parses against the closed schema. Comments without an `arena-repro` block are hidden.
2. `claim_hash` and `task_fps_hash` equal the claim's.
3. `scenario_version` equals the claim's.
4. `baseline.setup_fp` equals the claim's `setup_fp`.
5. `len(per_task) == len(tasks)`, and every count lies in `0..repeats`.
6. `Σb == baseline.passed`, and `baseline.trials == len(tasks) × repeats`. The same holds for `v` and the variant when
   present.
7. `errors + timeouts + budget_stopped == 0` for the baseline and the variant. **Post to thread is disabled for an
   incomplete or errored run**, with the reason.
8. When `variant` is present, `fingerprint(variant.setup) == variant.setup_fp`, and `variant.setup` has **one of two
   allowed shapes**:
   - **(a) role swap:** exactly one role's spec differs; params and decisions are identical.
   - **(b) control-policy swap (local app):** roles and params are identical; `decisions` differs, and the variant's
     `decisions` is a decision-service policy (`StudyTag(kind="swap", role="decisions", …)`, as `runner/study.py` tags
     it).

   Anything else is rejected. Each shape has a passing test and a failing test (e.g. two roles changed; a role and
   `decisions` changed together).
9. The comment is not edited.

These checks catch inconsistency and mistakes, not lies. The page labels reproductions "self-reported,
consistency-checked".

### 5. Trust strip statistics

- **Counted set:** the valid repros, deduplicated to the **latest per GitHub user**. The **author's own** repros are
  listed but excluded from the statistic.
- **Reproduced rate:** pooled baseline passes / pooled baseline trials across the counted set, with a **95% Wilson
  interval**, shown as "reproduced by N people at 86% [79–91]".
- **Below 2 people:** the strip shows each repro individually, with no interval.
- **The above-interval note** appears only with ≥ 3 distinct non-author reproducers **and** the claimed `pass_rate`
  above the pooled Wilson upper bound. Its wording states exactly that rule: "The claimed 91% is above the 95% interval
  of 3 independent reproductions [56–85%]." (24/33 pooled; the test asserts the computed Wilson bounds, not this string) It never says "above every reproduction", which can be false when the rule
  fires (e.g. repros at 100%, 60% and 60%). Test: that exact case renders the interval wording.
- **Engine:** repros are pooled across Pages and local. Each one carries an engine badge, and the strip can filter by
  engine.

### 6. Beat this: what runs

The claim becomes two explicit configs. `StudyConfig` (preset-based) is not used.

```python
configs = [
  PipelineConfig(name="claim-baseline", roles=refs(claim.setup), params=claim.setup["params"],
                 decisions=claim.setup["decisions"], study=StudyTag(kind="baseline")),
  PipelineConfig(name=f"swap-{role}", roles={**refs(claim.setup), role: candidate_ref}, params=…, decisions=…,
                 study=StudyTag(kind="swap", role=role, candidate=candidate_ref)),
]
ExperimentConfig(scenarios=[claim.scenario], configs=configs, task_ids=[t.id for t in claim.tasks],
                 repeats=claim.repeats, seed=claim.seed, max_cost_usd=cap, budget_mode="strict")
```

- `report/aggregate.py` already pairs configs by their `study` tags (line 210), so `ReplacementEffects` renders the
  paired result unchanged.
- **Swappable roles:**
  - Only roles the claim's setup actually calls: model roles always; decision roles (e.g. `email_assistant`'s `decider`,
    `escalation`) exactly when they appear in `DecisionConfig.llm_roles()` of the claim's decisions
    (`decisions/config.py:55`). A cascade with a Jev/Ollaya stage, or with no fallback, may call only one of them, or
    neither.
  - Pages offers OpenAI/Anthropic and named-endpoint candidates from the discovered catalog (re-review R15). The local app adds discovered Ollama and
    LM Studio models.
  - **The candidate inherits the replaced role's `max_tokens`**, appended as `#max_tokens=N` to `candidate_ref`. The
    card shows it, and the visitor can override it. Discovered specs have `max_tokens=None`, which strict mode would
    reject. Keeping the replaced role's value also makes the paired comparison differ in the model only. A
    candidate's `max_tokens` is part of `variant.setup_fp`. Tests:
    - a cloud candidate's resolved spec passes strict `validate_spec`;
    - the swap config's fingerprint includes the inherited `max_tokens`;
    - an override changes it.
  - **Decision services (Ollaya/Jev)** are a separate "swap control policy" control, in the local app only. That swap
    changes `decisions` instead of a role and is checked as shape (b) of rule 8. The check is on `variant.setup.decisions`
    directly: its policy is `jev` or `ollaya` (`DecisionConfig.services() == {policy}`), and every field other than the
    policy and that service's model equals its default. `StudyTag(role="decisions")` is only how the local app
    generates the swap.
- **Runnable here?** For each role in the baseline and candidate, the page checks that a key is present (Pages) or
  that the server is reachable (local), **and that the model appears in the discovered catalog for that key**.
  Otherwise it shows "model unavailable for your key" and disables Run.
- **Tests:**
  - the executed baseline's recomputed fingerprint equals `claim.setup_fp`;
  - a swap of an uncalled decision role is not offered;
  - the variant matches shape (a) or (b) of rule 8;
  - a portable claim passes strict `validate_spec`.

### 7. Cost

- Before Run, the page shows `estimate()` for baseline + variant.
- The cap defaults to **the estimate × 1.5**, and the visitor can edit it. Claim runs always use `budget_mode: strict`.
- If `estimate()` cannot price a model, or strict mode can't bound a call, Run is disabled with the model named.
- A run stopped by the cap shows its partial result locally and cannot be posted (rule 7).

### 8. Gist I/O

| | Pages | Local app |

| Reads | Unauthenticated (60/h) or with the token (5000/h) | Same, made by the server |

`Backend` gets `claim(ref)`, `claimThread(ref, page)`, `createClaim(runId)` and `postRepro(ref, runId)`. Both

### 9. Version drift and task drift

- **Task-changing version bump** (the current scenario version is newer, and its `regrades_from` doesn't include the
  claim's version): the claim shows read-only "made on v2; v3 changed the tasks or prompts". Run is disabled.
- **Grading-only bump** (the current version's `regrades_from` includes the claim's version): *(eng review D1:
  in-browser regrade deferred to v1.1)* the claim shows its original number read-only with "made on v2; grading
  changed since; reproductions now run v3. Author: run `arena regrade --apply` on the source run, then share it
  again." Run is disabled.
- **Same version, different tasks** (a claim task id is missing, or its fingerprint differs): the claim is refused with
  "task set changed without a version bump", which the page reports as a likely arena bug.

### 10. Opening a claim in the local app

- The claim card links to `http://127.0.0.1:8787/#/claim/…`. The port is visitor-editable and remembered per browser.
- **If the app isn't running**, the link fails with a connection error the Pages page can't see. So the card shows the
  hint next to the button, before the click: "Start it with `uv run arena ui --port <port>`, then click again."
- If the app answers 401, it stores the pending hash in `localStorage` (origin `127.0.0.1:<port>`, 10-minute expiry)
  and shows "run `uv run arena ui --link --port <port>` and open the printed link". The port is included because
  `--link` otherwise prints the default.
- After the token exchange creates the session, the app restores the pending hash. Tested.

## Open Questions

1. **The author controls the thread.** A gist owner can delete unfavorable reproduction comments. v1 accepts this and
   says so on the page. v2 option: reproducers also publish their own small `arena-repro` gist that links the claim,
   and the v2 aggregator indexes those independently of the author's thread. Decide before v2.
2. **Scenario version retention.** With traces, grading-only bumps are handled, but task-changing bumps strand old
   claims. Should `contracts/` keep the previous N versions' task data so old claims stay reproducible?
3. **Token UX.** GitHub's device-flow endpoints don't send CORS headers, so a static page can't use them without a
   proxy (a server, which premise 5 rules out). Real options for v1: a PAT on Pages, and `GITHUB_TOKEN` (or the
   `gh auth token` output) in the local app. Is pasting a PAT acceptable friction for the target dev, or does posting
   mostly happen from the local app?
4. **Model nondeterminism.** Should claims require `repeats ≥ 3`? That narrows the intervals but triples the cost per
   visit.
5. **Engine parity.** Repros are pooled across engines by default, which relies on the conformance vectors. Keep it
   pooled, or default to split?

## Success Criteria

- A claim made on Pages for a cloud-model setup opens on another machine. It re-runs baseline + variant within the
  strict cap and posts a reproduction that the original page counts on reload.
- The same claim link works in the local app through the server adapter, including after the token flow, which offers
  local models for the swap. The local app's CSP stays `connect-src 'self'` (an existing or new test pins the header).
- The executed baseline's fingerprint equals `claim.setup_fp` in a test with `ScriptedLLM`.
- Every rule in "A reproduction counts only if" has a passing and a failing test. Every edge state has a test. Unit
